# Архитектура данных «Мобильный мир»

Документ описывает данные магазина: коллекции MongoDB, шард-ключи и дальнейшие решения по нагрузке и консистентности. Учебный стенд в репозитории (`somedb.helloDoc`) показывает кластер и к этим коллекциям не относится. Доменные коллекции живут в базе `shop`.

## 7. Коллекции и шардирование

Шард-ключ у каждой коллекции — хеш поля, по которому идёт точечная операция. Диапазон по времени или по возрастающему идентификатору отправляет все новые записи в последний чанк: в пик это один шард. Коллекции шардируются пустыми, чтобы для хеш-ключа сразу появилось несколько чанков.

```javascript
sh.enableSharding("shop")
```

### 7.1 orders

Заказ — документ об одной покупке клиента.

| Поле | Тип | Смысл |
|---|---|---|
| `_id` | ObjectId | идентификатор заказа |
| `customer_id` | string | идентификатор клиента |
| `created_at` | date | дата и время оформления |
| `items` | array | `{ product_id: ObjectId, qty: int, price: Decimal128 }` — товары и цена на момент заказа |
| `status` | string | статус заказа |
| `total` | Decimal128 | сумма заказа |
| `zone` | string | геозона заказа, например `moscow` |

Шард-ключ: `{ customer_id: "hashed", _id: 1 }`.

Хеш `customer_id` раскладывает заказы разных клиентов по шардам, поэтому поток новых заказов не собирается в одном чанке. Суффикс `_id` даёт уникальность ключа и позволяет разрезать историю одного очень активного клиента. История клиента — запрос с равенством по `customer_id`, он попадает на шарды этого хеша, а не на весь кластер. Карточка из сессии читается по паре `{ customer_id, _id }` и идёт на шард клиента. Статус по одному `_id` таким ключом не направляется: это scatter-gather по всем шардам. Так ходят письмо и вебхук оплаты, у которых есть только идентификатор заказа.

`zone` и `created_at` в ключ не входят. Геозона концентрирует заказы Москвы на одном шарде и режет историю одного клиента. Диапазон по дате собирает все оформления «сейчас» в последний чанк.

| Операция | Фильтр | Маршрут |
|---|---|---|
| Создать заказ | insert, в документе есть `customer_id` | шард клиента |
| История клиента | `{ customer_id }` | шард клиента |
| Статус из сессии | `{ customer_id, _id }` | шард клиента |
| Статус по одному `_id` | `{ _id }` | все шарды |

```javascript
db.orders.createIndex({ customer_id: "hashed", _id: 1 })
sh.shardCollection("shop.orders", { customer_id: "hashed", _id: 1 })
db.orders.createIndex({ customer_id: 1, created_at: -1 })
```

Второй индекс отдаёт историю в порядке оформления. Поле `customer_id` в фильтре оставляет запрос на шарде клиента.

### 7.2 products

Товар — документ каталога с остатком по геозонам. Остатки зон лежат в одном документе, чтобы списание в одной зоне было одним обновлением.

| Поле | Тип | Смысл |
|---|---|---|
| `_id` | ObjectId | идентификатор товара |
| `name` | string | наименование |
| `category` | string | категория |
| `price` | Decimal128 | цена |
| `stock` | array | `{ zone: string, qty: int }` — остаток в геозоне |
| `attrs` | object | дополнительные атрибуты, например `{ color, size }` |

Пример: «Смартфон X», в `ekb` 50 штук, в `kgd` 30.

Шард-ключ: `{ _id: "hashed" }`.

Карточка товара и списание остатка ищут документ по `_id`. Хеш разносит разные товары по шардам, и обновления разных товаров не выстраиваются в один чанк. Один популярный `_id` остаётся одним документом на одном шарде; как его разгружать, сказано в разделе 8. Категория ключом не подходит: на «Электронику» приходится основная доля запросов, и весь этот поток сел бы на один шард. Цена и геозона тоже собирают популярный диапазон в одном месте. Фильтр каталога по категории и цене остаётся обычным индексом и выполняется на всех шардах — это плата за то, что запись остатка остаётся точечной.

| Операция | Фильтр | Маршрут |
|---|---|---|
| Карточка товара | `{ _id }` | один шард |
| Списание остатка | `{ _id }` и элемент `stock` нужной зоны | один шард |
| Каталог, категория и диапазон цен | `{ category, price }` | все шарды |

```javascript
db.products.createIndex({ _id: "hashed" })
sh.shardCollection("shop.products", { _id: "hashed" })
db.products.createIndex({ category: 1, price: 1 })
```

### 7.3 carts

Корзина — текущий набор товаров гостя или вошедшего пользователя. У гостя нет `user_id`, поэтому ключ владельца один: `owner_id`. Для гостя это `session_id`, для пользователя — `user_id`.

| Поле | Тип | Смысл |
|---|---|---|
| `_id` | ObjectId | идентификатор корзины |
| `owner_id` | string | `user_id` либо `session_id` |
| `user_id` | string или null | пользователь, у гостя пусто |
| `session_id` | string или null | сессия гостя |
| `items` | array | `{ product_id: ObjectId, quantity: int }` |
| `status` | string | `active`, `ordered`, `abandoned` |
| `created_at` | date | создание |
| `updated_at` | date | последнее изменение |
| `expires_at` | date | момент удаления устаревшей корзины |

Шард-ключ: `{ owner_id: "hashed" }`.

Чтение и правка идут фильтром `{ owner_id, status: "active" }` и попадают на один шард. Ключ `user_id` отправил бы все гостевые корзины (пустое значение) на один шард. Ключ `session_id` не находит корзину вошедшего пользователя. В паре с хешем высокая кардинальность `owner_id` размазывает и гостей, и пользователей.

Один активный набор на владельца держит приложение: `findOneAndUpdate` по `{ owner_id, status: "active" }` с upsert. Частичный уникальный индекс `{ owner_id: 1 }` на коллекции с ключом `{ owner_id: "hashed" }` MongoDB не примет — это другой ключ, не префикс шард-ключа.

TTL удаляет любой документ, у которого `expires_at` уже в прошлом, в том числе активный, если дата заполнена. У активной корзины поле пустое и сдвигается при каждом изменении. TTL забирает только `abandoned` и просроченных гостей. Обход идёт примерно раз в минуту.

Слияние читает гостевую корзину по `owner_id = session_id` и пользовательскую по `owner_id = user_id`. Количество одного `product_id` складывается один раз и записывается готовой суммой, без `$inc` поверх прошлой попытки. Гостевая помечается `abandoned` только после успешной записи пользовательской. Повтор не удваивает `quantity`: брошенная гостевая в сумму уже не входит. Корзины могут лежать на разных шардах.

| Операция | Фильтр | Маршрут |
|---|---|---|
| Создать корзину | insert с `owner_id` | шард владельца |
| Текущая корзина | `{ owner_id, status: "active" }` | шард владельца |
| Добавить, заменить, удалить товар | тот же фильтр | шард владельца |
| Отметить заказанной | тот же фильтр | шард владельца |
| Слить гостевую в пользовательскую | два `owner_id` | два шарда |

```javascript
db.carts.createIndex({ owner_id: "hashed" })
sh.shardCollection("shop.carts", { owner_id: "hashed" })
db.carts.createIndex({ expires_at: 1 }, { expireAfterSeconds: 0 })
```

### 7.4 Создание заказа и списание остатка

Заказ и остаток — разные коллекции с разными ключами, поэтому одна запись не атомарна на весь кластер. Распределённой транзакции на горячем пути нет. Клиент присылает `order_id`, он становится `_id` заказа. Условие сравнивает `qty` с заказанным количеством: проверка `$gte: 1` и `$inc: -1` при заказе двух штук уводит остаток в минус. Цена в заказ берётся из чтения документа на primary, а не с витрины.

Документ заказа пишется первым, со статусом `reserving`, и в нём уже лежат `created_at`, `month` и позиции с количеством. Падение процесса его не стирает. Списание и резерв — один `updateOne`. Фильтр `holds: { $not: { $elemMatch: { order_id: orderId } } }` пропускает обновление, только когда этого `order_id` в массиве нет. Сравнение `"holds.order_id": { $ne: orderId }` на массиве истинно, если в `holds` есть чужой заказ: на горячем товаре он есть почти всегда, и повтор снова делает `$inc`.

В том же запросе два массива, `stock` и `holds`. Позиционный `$` не различает, какой из них обновлять, поэтому зона списывается через `arrayFilters`.

```javascript
db.orders.insertOne({
  _id: orderId,
  status: "reserving",
  customer_id: customerId,
  created_at: createdAt,
  month: month,
  items: [{ product_id: productId, qty: orderedQty, price: priceFromPrimary, zone: "moscow" }],
  total: priceFromPrimary,
  zone: "moscow"
})

const taken = db.products.updateOne(
  {
    _id: productId,
    stock: { $elemMatch: { zone: "moscow", qty: { $gte: orderedQty } } },
    holds: { $not: { $elemMatch: { order_id: orderId } } }
  },
  {
    $inc: { "stock.$[s].qty": -orderedQty },
    $push: { holds: { order_id: orderId, qty: orderedQty, zone: "moscow" } }
  },
  { arrayFilters: [{ "s.zone": "moscow" }] }
)

const held = db.products.findOne({
  _id: productId,
  holds: { $elemMatch: { order_id: orderId } }
})

if (taken.matchedCount == 1 || held) {
  db.orders.updateOne(
    { _id: orderId, status: "reserving" },
    { $set: { status: "created" } }
  )
} else {
  db.orders.updateOne(
    { _id: orderId, status: "reserving" },
    { $set: { status: "rejected" } }
  )
}
```

`matchedCount == 1` — остаток списан в этом вызове, заказ становится `created`. `matchedCount == 0` и резерв с этим `order_id` уже лежит на товаре — повтор после падения: `$inc` не выполнился, заказ тоже становится `created`. `matchedCount == 0` и резерва нет — штук не хватает, заказ становится `rejected`.

Повтор начинает с чтения заказа по `_id`. Статус `created` значит, что списание уже было: повтор только снимает резерв, если он ещё на товаре, и выходит. Заказа нет — `insertOne` с тем же `_id` второй документ не создаёт, дальше то же списание. Если не списался второй товар, по первому обратный `$inc` идёт через тот же `arrayFilters` и только пока резерв на месте, затем резерв снимается `$pull`. Такой заказ в `created` не переводится.

## 8. Горячие шарды

Горячий шард — узел, на который приходится непропорциональная доля операций. Инцидент с «Электроникой»: около 70% запросов к товарам приходилось на один шард, потому что документы популярной категории лежали вместе. Ключ `{ _id: "hashed" }` из раздела 7 как раз разносит товары независимо от категории. Балансировщик это сам не лечит: он выравнивает объём данных, а не число запросов. Маленький шард с горячими карточками он не разгрузит.

`serverStatus`, `rs.status()` и profiler снимаются с primary шарда. `getShardDistribution()` — с mongos: на primary шарда этой команды нет. `serverStatus` на mongos показывает маршрутизатор, а не нагрузку шарда.

| Метрика | Откуда | Зачем |
|---|---|---|
| Скорость query и update | primary шарда, разность `serverStatus().opcounters` за 15 секунд | доля операций шарда в кластере |
| Лаг реплик шарда | primary шарда, `rs.status()`, разница `optimeDate` | перегруженный primary отстаёт по репликации первым |
| Объём и число документов | mongos, `getShardDistribution()` | перекос размера, с которым справляется балансировщик |
| Горячий `_id` | primary шарда, profiler (`slowms`), группировка медленных update по `_id` | какой документ греет шард |
| Грязный кеш WiredTiger | primary шарда, `serverStatus().wiredTiger.cache` | шард не успевает сбрасывать запись |
| Очередь лока | primary шарда, `serverStatus().globalLock.currentQueue` | операции ждут на этом узле |

`explain("executionStats")` полного запроса «Электроника» во время инцидента не запускается: он добавляет ту же нагрузку. Долю категории смотрят по плану без `executionStats` или агрегацией с лимитом.

Порог предупреждения: один шард дольше 10 минут держит больше 65% update кластера. 70%, как в инциденте с электроникой, — уже повод действовать. Дальше сравнение двух долей. Если доля документов и доля операций совпадают, это перекос размера. Если документов поровну, а операций нет — горячий ключ, перенос чанков ничего не даст.

```javascript
db.serverStatus().opcounters
db.serverStatus().globalLock.currentQueue
db.serverStatus().wiredTiger.cache["tracked dirty bytes in the cache"]

rs.status().members.map(m => ({ name: m.name, state: m.stateStr, optime: m.optimeDate }))

db.products.getShardDistribution()

db.setProfilingLevel(1, { slowms: 100 })
db.system.profile.aggregate([
  { $match: { ns: "shop.products", op: "update" } },
  { $group: { _id: "$command.updates.0.q._id", n: { $sum: 1 } } },
  { $sort: { n: -1 } },
  { $limit: 20 }
])
```

Profiler крутится на primary шарда. У команды `update` фильтр лежит в `command.updates.0.q._id`: группировка по `command.q._id` для такого документа пустая. Верхние `_id` — документы, которые греют узел.

### Что делать

Перекос размера выравнивает балансировщик, и только в тихое окно. В распродажу миграция чанков забирает диск и сеть у тех же шардов, которые и так не справляются, поэтому на время пика балансировщик выключен.

```javascript
use config
db.settings.updateOne(
  { _id: "balancer" },
  { $set: { activeWindow: { start: "22:00", stop: "02:00" } } },
  { upsert: true }
)

sh.stopBalancer()   // на время распродажи
sh.startBalancer()  // когда пик спал
```

Окно балансировщика — UTC config-сервера. `22:00`–`02:00` UTC это `01:00`–`05:00` по Москве, ночь магазина.

Категория, собранная на одном шарде, снимается сменой ключа на `{ _id: "hashed" }`. `reshardCollection` копирует коллекцию и держит вторую копию на диске, поэтому свободно нужно место примерно размером с коллекцию. Команда грузит кластер и запускается до распродажи, а не в момент 70%.

```javascript
sh.reshardCollection("shop.products", { _id: "hashed" })
```

После хеша по `_id` один популярный товар всё равно целиком живёт на одном шарде: один идентификатор не разрезается. Балансировщик и повторный reshard на тот же ключ его не размажут. Пока списания этого товара не греют шард, остатки всех зон лежат в одном документе, как в разделе 7.

Ключ `{ product_id: "hashed", zone: 1 }` не размазывает один товар в одной зоне: хеш `product_id` один, документ зоны один, и чанк не делится, пока в нём один документ. Зоны помогают, только если нагрузка уже размазана по зонам. Горячий товар одной зоны либо получает CPU и диск на своём шарде, либо остаток режется на buckets.

Поле `bucket` после хеша `product_id` не выносит эти документы в разные чанки: у одного товара один хеш, это одна точка ключа, и несколько коротких документов чанк не разрезают. В ключ хешируется строка `product_id:zone:bucket`. У каждого bucket свой хеш, предварительная нарезка hashed-ключа раскладывает их по шардам сразу. Запись называет свой `sku_bucket` и остаётся точечной. Чтение остатка — это чтение фиксированного числа buckets (их заранее немного) и сумма `qty`.

```javascript
db.product_stock.createIndex({ sku_bucket: "hashed" })
sh.shardCollection("shop.product_stock", { sku_bucket: "hashed" })
```

Чтение каталога в этот момент уводится на secondary и снимает query с горячего primary. Списание остатка остаётся на primary: продавать товар по устаревшему остатку нельзя. Остальные чтения разобраны в разделе 9. Пока идёт разбор, репликам горячего шарда добавляют CPU и диск: это снимает очередь сразу, а смена ключа убирает причину.

## 9. Чтение с реплик

Запись в любом случае принимает primary. Read preference выбирает, откуда читать. У клиента по умолчанию `primary`. На secondary уходят только те чтения, где отставание реплики не портит покупку. Каталог читается с `secondary`, не с `secondaryPreferred`. Если все реплики старше 90 секунд, запрос не возвращается на горячий primary: витрина отдаёт последнюю страницу из Redis, ограничивает параллелизм каталога или отвечает 503. Иначе отставание реплик вернуло бы на primary нагрузку, которую снимает раздел 8.

В шардированном кластере preference применяется внутри replica set каждого шарда. Каталог, который и так обходит все шарды, снимает query с каждого primary, а не с одного.

`maxStalenessSeconds` меньше 90 сервер не принимает, поэтому окно свежести реплики — 90 секунд. Для каталога и истории заказов этого хватает: цена, описание и список прошлых покупок за полторы минуты не ломают сценарий. Число остатка на витрине за эти 90 секунд может устареть, решение «продать» по нему не принимается.

| Операция | Коллекция | Откуда | Лаг | Почему |
|---|---|---|---|---|
| Каталог: категория и диапазон цен | products | secondary | до 90 с | Самое частое чтение. При лаге больше 90 с primary не трогаем: Redis, лимит параллелизма или 503 |
| Карточка: название и атрибуты | products | secondary | до 90 с | Страницу открывают чаще, чем меняют карточку. Цена с витрины в заказ не пишется |
| Цена в момент оформления | products | primary | 0 | Перечитывается в том же чтении `_id`, которым подтверждается списание |
| Число остатка на карточке | products | secondary | до 90 с | Цифра может отставать. Покупка на неё не опирается |
| Списание остатка | products | primary | 0 | Условный `updateOne` с проверкой `qty`. Чтение с реплики здесь продало бы товар, которого уже нет |
| История сразу после оформления | orders | primary | 0 | Сразу после вставки список этого клиента читается с primary, либо заказ показывается из ответа создания |
| История, когда клиент открывает её сам | orders | secondary | до 90 с | Список прошлых покупок. Лаг до 90 с здесь допустим |
| Статус заказа | orders | primary | 0 | Сразу после оформления и при каждой смене статуса клиент должен увидеть текущее значение, а не предыдущее |
| Текущая корзина | carts | primary | 0 | Экран открывают сразу после добавления товара. Реплика ещё без этой позиции покажет пустую или старую корзину |
| Чтение перед слиянием гостевой корзины | carts | primary | 0 | Обе корзины читаются и тут же пишутся. Устаревший `items` потеряет товар, положенный секунду назад |

```javascript
const catalog = connect("mongodb://mongos:27017/shop?readPreference=secondary&maxStalenessSeconds=90")
catalog.products.find({ category: "Электроника", price: { $gte: 1000, $lte: 5000 } })

const primary = connect("mongodb://mongos:27017/shop")
primary.orders.find({ customer_id: customerId, _id: orderId })
primary.carts.find({ owner_id: ownerId, status: "active" })
```

`maxStalenessSeconds` на соединении с `readPreference=primary` драйвер отвергает. Свежесть задаётся только каталогу и поздней истории, на втором соединении её нет.

В pymongo то же самое задаётся на коллекции. Каталог получает `Secondary(max_staleness=90)`, поздняя история — тоже. `max_staleness` — целое число секунд, минимум 90. Корзина, статус заказа, цена при списании и история сразу после создания остаются на `Primary`. Если все secondary старше 90 секунд, каталог на primary не переключается.

## 10. Cassandra

На чёрной пятнице кластер MongoDB был шардирован по диапазону. На 50 тысячах запросов в секунду добавление шарда заново раскладывало чанки по всем узлам, и латентность просела из-за переноса, а не из-за самой покупки. Хеш-ключ из раздела 7 убирает горячий последний чанк, но новый шард в Mongo всё равно получает данные переносом. В Cassandra партиция закреплена за диапазоном токенов. Новый узел забирает примерно `1/(N+1)` данных, остальные партиции остаются на месте.

### 10.1 Что переносим

Целостность покупки важнее скорости раскладки. Остаток товара и заказ в момент оформления остаются в Mongo: списание — условная запись на primary, и потерянное сравнение «хватит ли штук» продаёт отсутствующий товар. Экран статуса сразу после оплаты тоже остаётся на primary Mongo, как в разделе 9. Каталог по категории в Cassandra не переносится: ключ-категория снова собрал бы «Электронику» в одну партицию.

В Cassandra уходят данные, которых много, которые дописываются и которые должны пережить новый узел без полной перекладки.

| Данные | Куда | Почему |
|---|---|---|
| Остаток и оформление заказа | Mongo | Нужна условная запись на один документ. Легковесные транзакции Cassandra на горячем товаре сами становятся узким местом |
| Статус только что созданного заказа | Mongo, primary | Клиент читает свою же запись |
| История заказов | Cassandra | Дописываемый журнал по клиенту, чтение списка терпит секунды, как вторичное чтение в разделе 9 |
| Корзины | Cassandra | Много гостевых записей, короткая жизнь, правка одной позиции не должна переписывать всю корзину |
| Сессии | Cassandra | Высокая кардинальность, запись с TTL, потеря сессии лишь разлогинивает гостя |

### 10.2 Ключи

Приложение, шлюз и Mongo стоят в одном месте, на схеме это Москва. `europe` и `asia` — холодные копии: пока приложение не переехало, их никто не читает. `LOCAL_QUORUM` — кворум Москвы. Если магазин поднимают в другом дата-центре, он читает локальные реплики того дата-центра. `NetworkTopologyStrategy` хранит три реплики в каждом, запись не ждёт другой регион.

```cql
CREATE KEYSPACE shop WITH replication = {
  'class': 'NetworkTopologyStrategy',
  'moscow': 3,
  'europe': 3,
  'asia': 3
};
```

Партиционный ключ везде высокой кардинальности: клиент и месяц, владелец корзины, сессия. Дата, геозона и категория партицией не становятся. Дата стоит в кластерном ключе и сортирует строки внутри одной партиции. При добавлении узла переезжают только партиции его новых диапазонов токенов (`num_tokens: 16`), после ввода на старых узлах выполняется `nodetool cleanup`. Полный repair в распродажу не запускается: он грузит кластер так же, как перенос чанков Mongo.

История заказов — одна строка на заказ. Месяц в партиционном ключе не даёт партиции расти вместе с клиентом: текущий месяц читается одним запросом, более старые — когда пользователь листает дальше. Кластерный порядок отдаёт последние заказы месяца первыми.

```cql
CREATE TYPE shop.order_item (
  product_id uuid,
  qty int,
  price decimal
);

CREATE TABLE shop.orders_by_customer (
  customer_id text,
  month text,
  created_at timestamp,
  order_id uuid,
  status text,
  total decimal,
  zone text,
  items frozen<list<frozen<shop.order_item>>>,
  PRIMARY KEY ((customer_id, month), created_at, order_id)
) WITH CLUSTERING ORDER BY (created_at DESC, order_id ASC);
```

Колонка `status` — снимок на момент записи строки. Живой статус читается только из Mongo. Каждая смена статуса дописывается той же строкой: `UPDATE ... SET status = ? WHERE customer_id = ? AND month = ? AND created_at = ? AND order_id = ?`. Иначе список истории показывает статус оформления, а экран заказа — другой.

Вставка заказа в Mongo и строка истории — две записи. Первичный ключ строки — `(customer_id, month, created_at, order_id)`. Одного `order_id` мало: повтор с новым `now()` попадает в другой `month` и другой `created_at` и пишет вторую строку. `month` и `created_at` фиксируются в документе Mongo со статусом `reserving` и оттуда же читаются при повторе. Повтор — тот же `INSERT` с этими четырьмя полями, Cassandra перезаписывает одну строку. Если Mongo прошла, а Cassandra нет, приложение повторяет эту вставку, пока она не подтвердится. Обратный порядок не используется: история без заказа в Mongo показала бы покупку, которой нет.

Корзина — строка на пару «владелец, товар». Добавление и удаление позиции это запись одной строки, а не чтение и перезапись всего списка. Слияние гостевой корзины в пользовательскую читает одну партицию и пишет другую. Количество одного `product_id` складывается. Строки гостя удаляются только после успешной копии: повтор без удаления удвоил бы количество.

Табличный TTL на позициях старит каждую строку отдельно, и нетронутая позиция исчезнет, пока соседние живы. Срок живёт в `cart_headers`: у строки `default_time_to_live` 30 суток, у `cart_items` своего TTL нет. Любое изменение корзины заново пишет заголовок того же `owner_id` и тем самым сбрасывает его TTL. Когда заголовка нет, партицию позиций не показывают. После оформления строки `cart_items` удаляются, и только после идемпотентной вставки заказа. Удаление раньше вставки теряет корзину, если заказ не записался.

```cql
CREATE TABLE shop.cart_headers (
  owner_id text PRIMARY KEY,
  updated_at timestamp
) WITH default_time_to_live = 2592000;

CREATE TABLE shop.cart_items (
  owner_id text,
  product_id uuid,
  quantity int,
  updated_at timestamp,
  PRIMARY KEY ((owner_id), product_id)
);

CREATE TABLE shop.sessions (
  session_id text PRIMARY KEY,
  user_id text,
  created_at timestamp
) WITH default_time_to_live = 604800;
```

### 10.3 Целостность

Hinted handoff, блокирующий read repair и anti-entropy repair закрывают разные дыры. Hinted handoff включён на кластере для всех таблиц keyspace: координатор недолго держит запись для выключенной реплики и досылает её, когда узел вернулся. Подсказки живут часы и не заменяют repair. Read repair в Cassandra 4 срабатывает само, когда чтение с кворумом видит разные дайджесты. Отдельный процент read repair больше не задаётся. Anti-entropy (`nodetool repair`) сверяет реплики деревьями Меркла и на потоке распродажи даёт ту же просадку, от которой уходим.

| Данные | Запись и чтение | Hinted handoff | Read repair | Anti-entropy |
|---|---|---|---|---|
| История заказов | `LOCAL_QUORUM` | да, короткий простой реплики | да: кворум сравнивает реплики, расхождение снимка статуса чинится на этом чтении | да, раз в неделю вне пика. У истории нет TTL, потерянная мутация оставляет дыру навсегда |
| Корзина | `LOCAL_QUORUM` | да | да, тот же кворум. Экран корзины должен увидеть только что записанную позицию внутри своего дата-центра | полный repair в распродажу не запускаем. Протухший заголовок прячет брошенную корзину, инкрементальный repair идёт ночью |
| Сессия | `LOCAL_ONE` | да | нет. Сессию пишет один клиент, кворум только добавляет задержку, а протухшая сессия и так исчезнет по TTL | нет. Чистка — TTL |

`LOCAL_QUORUM` при факторе 3 отвечает после двух локальных реплик. История и корзина платят этой задержкой, чтобы подтверждённая запись читалась в том же дата-центре. Сессия пишется в одну реплику: гость при сбое получит новую сессию, заказ из-за этого не пропадёт. Статус на экране сразу после оплаты по-прежнему читается из Mongo.
