# Архитектура данных «Мобильный мир»

Документ описывает данные магазина: коллекции MongoDB, шард-ключи и дальнейшие решения по нагрузке и консистентности. Учебный стенд в репозитории (`somedb.helloDoc`) показывает кластер и к этим коллекциям не относится. Доменные коллекции живут в базе `shop`.

## 7. Коллекции и шардирование

Шард-ключ у каждой коллекции — хеш поля, по которому идёт точечная операция. Диапазон по времени или по возрастающему идентификатору отправляет все новые записи в последний чанк: в пик это один шард. Коллекции шардируются пустыми, чтобы для хеш-ключа сразу появилось несколько чанков.

```javascript
sh.enableSharding("shop")
```

### 7.1 orders

Заказ — документ об одной покупке клиента.

| Поле | Тип | Смысл |
|---|---|---|
| `_id` | ObjectId | идентификатор заказа |
| `customer_id` | string | идентификатор клиента |
| `created_at` | date | дата и время оформления |
| `items` | array | `{ product_id: ObjectId, qty: int, price: Decimal128 }` — товары и цена на момент заказа |
| `status` | string | статус заказа |
| `total` | Decimal128 | сумма заказа |
| `zone` | string | геозона заказа, например `moscow` |

Шард-ключ: `{ customer_id: "hashed", _id: 1 }`.

Хеш `customer_id` раскладывает заказы разных клиентов по шардам, поэтому поток новых заказов не собирается в одном чанке. Суффикс `_id` даёт уникальность ключа и позволяет разрезать историю одного очень активного клиента. История клиента — запрос с равенством по `customer_id`, он попадает на шарды этого хеша, а не на весь кластер. Карточка заказа читается по паре `{ customer_id, _id }`: идентификатор клиента есть в сессии, отдельный поиск по одному `_id` не нужен.

`zone` и `created_at` в ключ не входят. Геозона концентрирует заказы Москвы на одном шарде и режет историю одного клиента. Диапазон по дате собирает все оформления «сейчас» в последний чанк.

| Операция | Фильтр | Маршрут |
|---|---|---|
| Создать заказ | insert, в документе есть `customer_id` | шард клиента |
| История клиента | `{ customer_id }` | шард клиента |
| Статус заказа | `{ customer_id, _id }` | шард клиента |

```javascript
db.orders.createIndex({ customer_id: "hashed", _id: 1 })
sh.shardCollection("shop.orders", { customer_id: "hashed", _id: 1 })
db.orders.createIndex({ customer_id: 1, created_at: -1 })
```

Второй индекс отдаёт историю в порядке оформления. Поле `customer_id` в фильтре оставляет запрос на шарде клиента.

### 7.2 products

Товар — документ каталога с остатком по геозонам. Остатки зон лежат в одном документе, чтобы списание в одной зоне было одним обновлением.

| Поле | Тип | Смысл |
|---|---|---|
| `_id` | ObjectId | идентификатор товара |
| `name` | string | наименование |
| `category` | string | категория |
| `price` | Decimal128 | цена |
| `stock` | array | `{ zone: string, qty: int }` — остаток в геозоне |
| `attrs` | object | дополнительные атрибуты, например `{ color, size }` |

Пример: «Смартфон X», в `ekb` 50 штук, в `kgd` 30.

Шард-ключ: `{ _id: "hashed" }`.

Карточка товара и списание остатка ищут документ по `_id`. Хеш разносит товары равномерно, и обновления остатков не выстраиваются в один чанк. Категория ключом не подходит: на «Электронику» приходится основная доля запросов, и весь этот поток сел бы на один шард. Цена и геозона тоже собирают популярный диапазон в одном месте. Фильтр каталога по категории и цене остаётся обычным индексом и выполняется на всех шардах — это плата за то, что запись остатка остаётся точечной.

| Операция | Фильтр | Маршрут |
|---|---|---|
| Карточка товара | `{ _id }` | один шард |
| Списание остатка | `{ _id }` и элемент `stock` нужной зоны | один шард |
| Каталог, категория и диапазон цен | `{ category, price }` | все шарды |

```javascript
db.products.createIndex({ _id: "hashed" })
sh.shardCollection("shop.products", { _id: "hashed" })
db.products.createIndex({ category: 1, price: 1 })
```

### 7.3 carts

Корзина — текущий набор товаров гостя или вошедшего пользователя. У гостя нет `user_id`, поэтому ключ владельца один: `owner_id`. Для гостя это `session_id`, для пользователя — `user_id`.

| Поле | Тип | Смысл |
|---|---|---|
| `_id` | ObjectId | идентификатор корзины |
| `owner_id` | string | `user_id` либо `session_id` |
| `user_id` | string или null | пользователь, у гостя пусто |
| `session_id` | string или null | сессия гостя |
| `items` | array | `{ product_id: ObjectId, quantity: int }` |
| `status` | string | `active`, `ordered`, `abandoned` |
| `created_at` | date | создание |
| `updated_at` | date | последнее изменение |
| `expires_at` | date | момент удаления устаревшей корзины |

Шард-ключ: `{ owner_id: "hashed" }`.

Чтение и правка идут фильтром `{ owner_id, status: "active" }` и попадают на один шард. Ключ `user_id` отправил бы все гостевые корзины (пустое значение) на один шард. Ключ `session_id` не находит корзину вошедшего пользователя. В паре с хешем высокая кардинальность `owner_id` размазывает и гостей, и пользователей.

Один активный набор на владельца держит частичный уникальный индекс. Префикс индекса совпадает с шард-ключом, поэтому уникальность на шардированной коллекции допустима. Старые корзины забирает TTL: документ удаляется, когда наступает `expires_at`. Обход TTL идёт примерно раз в минуту, для брошенных корзин этой задержки достаточно.

Слияние при входе — две точечные операции. Приложение читает гостевую корзину по `owner_id = session_id`, дописывает `items` в корзину `owner_id = user_id` и помечает гостевую `abandoned`. Корзины могут лежать на разных шардах, общего документа у них нет.

| Операция | Фильтр | Маршрут |
|---|---|---|
| Создать корзину | insert с `owner_id` | шард владельца |
| Текущая корзина | `{ owner_id, status: "active" }` | шард владельца |
| Добавить, заменить, удалить товар | тот же фильтр | шард владельца |
| Отметить заказанной | тот же фильтр | шард владельца |
| Слить гостевую в пользовательскую | два `owner_id` | два шарда |

```javascript
db.carts.createIndex({ owner_id: "hashed" })
sh.shardCollection("shop.carts", { owner_id: "hashed" })
db.carts.createIndex(
  { owner_id: 1 },
  { unique: true, partialFilterExpression: { status: "active" } }
)
db.carts.createIndex({ expires_at: 1 }, { expireAfterSeconds: 0 })
```

### 7.4 Создание заказа и списание остатка

Заказ и остаток — разные коллекции с разными ключами, поэтому одна запись не атомарна на весь кластер. Сначала условное списание на шарде товара: документ уменьшается, только если в зоне хватает штук. Затем вставка заказа на шард клиента. Если вставка не прошла, приложение возвращает остаток тем же точечным `$inc`. Так горячий путь не ждёт распределённую транзакцию.

```javascript
db.products.updateOne(
  { _id: productId, stock: { $elemMatch: { zone: "moscow", qty: { $gte: 1 } } } },
  { $inc: { "stock.$.qty": -1 } }
)

db.orders.insertOne({
  customer_id: customerId,
  created_at: new Date(),
  items: [{ product_id: productId, qty: 1, price: NumberDecimal("1990.00") }],
  status: "created",
  total: NumberDecimal("1990.00"),
  zone: "moscow"
})
```

`matchedCount == 0` у первого вызова означает, что в зоне товара уже нет. Заказ в этом случае не создаётся.

## 8. Горячие шарды

Горячий шард — узел, на который приходится непропорциональная доля операций. Инцидент с «Электроникой»: около 70% запросов к товарам приходилось на один шард, потому что документы популярной категории лежали вместе. Ключ `{ _id: "hashed" }` из раздела 7 как раз разносит товары независимо от категории. Балансировщик это сам не лечит: он выравнивает объём данных, а не число запросов. Маленький шард с горячими карточками он не разгрузит.

Снимать метрики нужно с primary каждого шарда. `serverStatus` на mongos показывает маршрутизатор, а не нагрузку шарда.

| Метрика | Откуда | Зачем |
|---|---|---|
| Скорость query и update | разность `serverStatus().opcounters` за 15 секунд | доля операций шарда в кластере |
| Лаг реплик шарда | `rs.status()`, разница `optimeDate` primary и secondary | перегруженный primary отстаёт по репликации первым |
| Объём и число документов | `getShardDistribution()` | перекос размера, с которым справляется балансировщик |
| Доля категории по шардам | `explain` запроса `{ category: "Электроника" }` | категория всё ещё лежит на одном шарде |
| Грязный кеш WiredTiger | `serverStatus().wiredTiger.cache` | шард не успевает сбрасывать запись |
| Очередь лока | `serverStatus().globalLock.currentQueue` | операции ждут на этом узле |

Порог предупреждения: один шард дольше 10 минут держит больше 65% update кластера. 70%, как в инциденте с электроникой, — уже повод действовать. Дальше сравнение двух долей. Если доля документов и доля операций совпадают, это перекос размера. Если документов поровну, а операций нет — горячий ключ, перенос чанков ничего не даст.

```javascript
db.serverStatus().opcounters
db.serverStatus().globalLock.currentQueue
db.serverStatus().wiredTiger.cache["tracked dirty bytes in the cache"]

rs.status().members.map(m => ({ name: m.name, state: m.stateStr, optime: m.optimeDate }))

db.products.getShardDistribution()

db.products.find({ category: "Электроника" }).explain("executionStats")
```

В `explain` смотреть `nReturned` по каждому шарду. Когда у одного шарда около 70% документов категории, ключ всё ещё собирает категорию вместе.

### Что делать

Перекос размера выравнивает балансировщик, и только в тихое окно. В распродажу миграция чанков забирает диск и сеть у тех же шардов, которые и так не справляются, поэтому на время пика балансировщик выключен.

```javascript
use config
db.settings.updateOne(
  { _id: "balancer" },
  { $set: { activeWindow: { start: "01:00", stop: "05:00" } } },
  { upsert: true }
)

sh.stopBalancer()   // на время распродажи
sh.startBalancer()  // когда пик спал
```

Категория, собранная на одном шарде, снимается сменой ключа на `{ _id: "hashed" }`. `reshardCollection` копирует коллекцию и тоже грузит кластер, поэтому команда запускается до распродажи, а не в момент 70%.

```javascript
sh.reshardCollection("shop.products", { _id: "hashed" })
```

После хеша по `_id` один популярный товар всё равно целиком живёт на одном шарде: один идентификатор не разрезается. Балансировщик и повторный reshard на тот же ключ его не размажут. Пока списания этого товара не греют шард, остатки всех зон лежат в одном документе, как в разделе 7. Если мониторинг показывает один `_id`, остатки только этого товара разносятся по документам зон. Покупка списывает одну зону и остаётся одним обновлением, а зоны одного товара могут уехать на разные шарды.

```javascript
db.product_stock.createIndex({ product_id: "hashed", zone: 1 })
sh.shardCollection("shop.product_stock", { product_id: "hashed", zone: 1 })
```

Чтение каталога в этот момент уводится на secondary и снимает query с горячего primary. Списание остатка остаётся на primary: продавать товар по устаревшему остатку нельзя. Остальные чтения разобраны в разделе 9. Пока идёт разбор, репликам горячего шарда добавляют CPU и диск: это снимает очередь сразу, а смена ключа убирает причину.

## 9. Чтение с реплик

Запись в любом случае принимает primary. Read preference выбирает, откуда читать. У клиента по умолчанию `primary`. На secondary уходят только те чтения, где отставание реплики не портит покупку. Режим `secondaryPreferred`: реплика читается, пока она достаточно свежая, иначе запрос возвращается на primary и каталог не падает из-за отставшей реплики.

В шардированном кластере preference применяется внутри replica set каждого шарда. Каталог, который и так обходит все шарды, снимает query с каждого primary, а не с одного.

`maxStalenessSeconds` меньше 90 сервер не принимает, поэтому окно свежести реплики — 90 секунд. Для каталога и истории заказов этого хватает: цена, описание и список прошлых покупок за полторы минуты не ломают сценарий. Число остатка на витрине за эти 90 секунд может устареть, решение «продать» по нему не принимается.

| Операция | Коллекция | Откуда | Лаг | Почему |
|---|---|---|---|---|
| Каталог: категория и диапазон цен | products | secondaryPreferred | до 90 с | Самое частое чтение, описание категории меняется редко. В инциденте с «Электроникой» эти query как раз забивали primary |
| Карточка: название, цена, атрибуты | products | secondaryPreferred | до 90 с | Страницу открывают чаще, чем меняют карточку |
| Число остатка на карточке | products | secondaryPreferred | до 90 с | Цифра может отставать. Покупка на неё не опирается |
| Списание остатка | products | primary | 0 | Условный `updateOne` с проверкой `qty`. Чтение с реплики здесь продало бы товар, которого уже нет |
| История заказов клиента | orders | secondaryPreferred | до 90 с | Список прошлых покупок. Только что созданный заказ на этот экран не выводят |
| Статус заказа | orders | primary | 0 | Сразу после оформления и при каждой смене статуса клиент должен увидеть текущее значение, а не предыдущее |
| Текущая корзина | carts | primary | 0 | Экран открывают сразу после добавления товара. Реплика ещё без этой позиции покажет пустую или старую корзину |
| Чтение перед слиянием гостевой корзины | carts | primary | 0 | Обе корзины читаются и тут же пишутся. Устаревший `items` потеряет товар, положенный секунду назад |

```javascript
db = connect("mongodb://mongos:27017/shop?readPreference=secondaryPreferred&maxStalenessSeconds=90")
db.products.find({ category: "Электроника", price: { $gte: 1000, $lte: 5000 } })

db.orders.find({ customer_id: customerId, _id: orderId }).readPref("primary")
db.carts.find({ owner_id: ownerId, status: "active" }).readPref("primary")
```

В приложении на pymongo то же самое задаётся на коллекции, а не на всё соединение. Каталог и история получают `SecondaryPreferred(max_staleness=90)`, корзина, статус заказа и списание остаются на `Primary`.

## 10. Cassandra

На чёрной пятнице кластер MongoDB был шардирован по диапазону. На 50 тысячах запросов в секунду добавление шарда заново раскладывало чанки по всем узлам, и латентность просела из-за переноса, а не из-за самой покупки. Хеш-ключ из раздела 7 убирает горячий последний чанк, но новый шард в Mongo всё равно получает данные переносом. В Cassandra партиция закреплена за диапазоном токенов. Новый узел забирает примерно `1/(N+1)` данных, остальные партиции остаются на месте.

### 10.1 Что переносим

Целостность покупки важнее скорости раскладки. Остаток товара и заказ в момент оформления остаются в Mongo: списание — условная запись на primary, и потерянное сравнение «хватит ли штук» продаёт отсутствующий товар. Экран статуса сразу после оплаты тоже остаётся на primary Mongo, как в разделе 9. Каталог по категории в Cassandra не переносится: ключ-категория снова собрал бы «Электронику» в одну партицию.

В Cassandra уходят данные, которых много, которые дописываются и которые должны пережить новый узел без полной перекладки.

| Данные | Куда | Почему |
|---|---|---|
| Остаток и оформление заказа | Mongo | Нужна условная запись на один документ. Легковесные транзакции Cassandra на горячем товаре сами становятся узким местом |
| Статус только что созданного заказа | Mongo, primary | Клиент читает свою же запись |
| История заказов | Cassandra | Дописываемый журнал по клиенту, чтение списка терпит секунды, как вторичное чтение в разделе 9 |
| Корзины | Cassandra | Много гостевых записей, короткая жизнь, правка одной позиции не должна переписывать всю корзину |
| Сессии | Cassandra | Высокая кардинальность, запись с TTL, потеря сессии лишь разлогинивает гостя |

### 10.2 Ключи

Ключевое пространство повторяет регионы схемы CDN. `NetworkTopologyStrategy` хранит три реплики в каждом дата-центре, запись с `LOCAL_QUORUM` подтверждается локально и не ждёт другой регион.

```cql
CREATE KEYSPACE shop WITH replication = {
  'class': 'NetworkTopologyStrategy',
  'moscow': 3,
  'europe': 3,
  'asia': 3
};
```

Партиционный ключ везде высокой кардинальности: клиент, владелец корзины, сессия. Дата, геозона и категория партицией не становятся. Дата стоит в кластерном ключе и сортирует строки внутри одной партиции. Один очень активный клиент занимает одну партицию, а не шард со всей Москвой. При добавлении узла переезжают только партиции его новых диапазонов токенов (`num_tokens: 16`), после ввода на старых узлах выполняется `nodetool cleanup`. Полный repair в распродажу не запускается: он грузит кластер так же, как перенос чанков Mongo.

История заказов — одна строка на заказ. Кластерный порядок отдаёт последние заказы первыми, без сбора по всему кольцу.

```cql
CREATE TYPE shop.order_item (
  product_id uuid,
  qty int,
  price decimal
);

CREATE TABLE shop.orders_by_customer (
  customer_id text,
  created_at timestamp,
  order_id uuid,
  status text,
  total decimal,
  zone text,
  items frozen<list<frozen<shop.order_item>>>,
  PRIMARY KEY ((customer_id), created_at, order_id)
) WITH CLUSTERING ORDER BY (created_at DESC, order_id ASC);
```

Корзина — строка на пару «владелец, товар». Добавление и удаление позиции это запись одной строки, а не чтение и перезапись всего списка. Слияние гостевой корзины в пользовательскую читает одну партицию и пишет другую. Заброшенные корзины забирает TTL, как `expires_at` в Mongo.

```cql
CREATE TABLE shop.cart_items (
  owner_id text,
  product_id uuid,
  quantity int,
  updated_at timestamp,
  PRIMARY KEY ((owner_id), product_id)
) WITH default_time_to_live = 2592000;
```

### 10.3 Целостность

Hinted handoff, блокирующий read repair и anti-entropy repair закрывают разные дыры. Hinted handoff включён на кластере для всех трёх таблиц: координатор недолго держит запись для выключенной реплики и досылает её, когда узел вернулся. Подсказки живут часы и не заменяют repair. Read repair в Cassandra 4 срабатывает само, когда чтение с кворумом видит разные дайджесты. Отдельный процент read repair больше не задаётся. Anti-entropy (`nodetool repair`) сверяет реплики деревьями Меркла и на потоке распродажи даёт ту же просадку, от которой уходим.

| Данные | Запись и чтение | Hinted handoff | Read repair | Anti-entropy |
|---|---|---|---|---|
| История заказов | `LOCAL_QUORUM` | да, короткий простой реплики | да: кворум сравнивает реплики, расхождение статуса в списке чинится на этом чтении | да, раз в неделю вне пика. У истории нет TTL, потерянная мутация оставляет дыру навсегда |
| Корзина | `LOCAL_QUORUM` | да | да, тот же кворум. Экран корзины должен увидеть только что записанную позицию внутри своего дата-центра | полный repair в распродажу не запускаем. TTL удаляет брошенные корзины, инкрементальный repair идёт ночью |
| Сессия | `LOCAL_ONE` | да | нет. Сессию пишет один клиент, кворум только добавляет задержку, а протухшая сессия и так исчезнет по TTL | нет. Чистка — TTL |

`LOCAL_QUORUM` при факторе 3 отвечает после двух локальных реплик. История и корзина платят этой задержкой, чтобы подтверждённая запись читалась в том же дата-центре. Сессия пишется в одну реплику: гость при сбое получит новую сессию, заказ из-за этого не пропадёт. Статус на экране сразу после оплаты по-прежнему читается из Mongo.
